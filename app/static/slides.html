Kueue · job queueing for Kubernetes

Who gets the GPU next?

GPUs are scarce and expensive, and every team wants one now. Kueue gives a Kubernetes cluster a waiting line with rules, so the answer is never "whoever submitted first".

The problem

Kubernetes has no waiting line for jobs

Kubernetes schedules pods one at a time. When a shared GPU cluster is full, four things go wrong.

Nobody can see the line

A job that doesn't fit just has pods stuck in Pending. There is no list of who is next or how long the wait is.

Quota says no, not "wait"

ResourceQuota blocks new pods once a team is over its limit. It can't hold the job and start it later.

Priority means eviction

Pod priority gets urgent work in by evicting running pods. An evicted training run loses everything since its last checkpoint.

Cost follows whoever submits most

Every Pending pod can trigger a new GPU node. With no cap, a sweep of 50 experiments can ask for 50 GPUs.

What Kueue is

Kueue decides when a job starts

Kueue is an open-source Kubernetes project (kubernetes-sigs) that adds a job queue and quotas to a cluster. It works with the scheduler; it doesn't replace it.

When

Kueue

Holds jobs in line and lets each one start when there is quota for it.

Where

Kubernetes scheduler

Places the pods of a started job onto nodes, exactly as it does today.

On what

GKE ComputeClass

Creates the right GPU nodes for those pods and removes them when they sit idle.

Works with the job types teams already use: Kubernetes Job, JobSet, Kubeflow training jobs, Ray and more.

How it works

A job waits paused until there is room

  1. 1

    Submit

    A normal Kubernetes Job with one extra label naming the queue. It is created paused, so no pods and no nodes yet.

  2. 2

    Line up

    Kueue puts it in line: higher priority first, then first come, first served.

  3. 3

    Admit

    When quota is free, Kueue un-pauses the job and tells it which kind of hardware to run on.

  4. 4

    Run and release

    The job runs to the end. Its quota is freed and the next job in line starts.

The only change to an existing Job is the label kueue.x-k8s.io/queue-name. The training code stays the same.

Building blocks

Four objects describe the whole policy

LocalQueue

The door a team submits to, inside its own namespace.

In this demo: training-queue

ClusterQueue

The shared pool and its limits: how much CPU, memory and GPU can be in use at once.

In this demo: 4 GPU seats

WorkloadPriorityClass

Order in the line. It changes who goes next, not which running pods get evicted.

In this demo: urgent 1000, regular 100

ResourceFlavor

The kind of hardware behind the quota, so admitted jobs land on the right nodes.

In this demo: the L4 / T4 time-shared ComputeClass

Before and after

What changes on a shared GPU cluster

Without Kueue

  • Jobs that don't fit sit Pending, in no visible order
  • Urgent work waits its turn, or evicts running jobs
  • Teams compete for GPUs with no fair limit
  • GPU nodes scale with whatever gets submitted

With Kueue

  • One visible line: who is running and who is next
  • Urgent work goes to the front; running jobs can be left to finish
  • Each team or pool has a quota, and can lend what it isn't using
  • Only admitted jobs get nodes, so spend is capped by quota

In this demo

One GPU, four seats, and an urgent job

A single low-cost GPU on GKE is time-shared by up to four small training jobs. Kueue manages the line for those four seats.

  1. 1

    Send 6 regular jobs

    Four start on the shared GPU. Two wait in line.

  2. 2

    Send an urgent job

    It moves to first in line. Nothing that is running gets stopped.

  3. 3

    A seat frees up

    The urgent job takes it, ahead of the two regular jobs that were waiting longer.

Kueue can also stop lower-priority jobs to make room. This demo turns that off on purpose (preemption: Never) so no training progress is lost.
